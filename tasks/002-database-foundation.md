# 002. PostgreSQL, миграции и модель хранения

**Этап:** 1. Технический фундамент

## Цель

Создать безопасную схему PostgreSQL и процесс её эволюции для всех предметных модулей.

## Контекст продукта

PostgreSQL является единственным источником достоверных медицинских, финансовых, расписательных и аудиторских данных.

## Объём

- Подключить Worker к PostgreSQL/Supabase через Hyperdrive и Workers-совместимый драйвер.
- Настроить Drizzle ORM/Kit и контролируемые SQL-миграции.
- Заложить UUIDv7, `timestamptz`, версии строк, архивные признаки и связи основных доменов PRD.
- Создать отдельные роли runtime и migrations и закрытую предметную схему.

## Вне объёма

Наполнение доменной логикой, отдельный поисковый сервер, пользовательский backup-модуль.

## Требования

- Runtime имеет минимальные права; предметные таблицы не публикуются через Supabase Data API.
- Критические ограничения выражаются в БД, когда одной прикладной проверки недостаточно.
- Hyperdrive-кэш отключён для запросов, которым нужна актуальность после записи.

## Критерии приёмки

- Миграции поднимают пустую local/preview БД и повторно применяются предсказуемо.
- Все точные моменты сохраняются в UTC; тест подтверждает отображение в часовом поясе клиники.
- Runtime не может менять схему и не имеет прямого доступа к закрытым административным операциям.
- Схема поддерживает объёмы 50 000 пациентов и 500 000 записей с необходимыми индексами.
