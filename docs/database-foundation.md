# PostgreSQL: технический фундамент

Предметные таблицы находятся только в `crm`; закрытый журнал — в `crm_internal.schema_migrations`. `crm_runtime` не имеет `USAGE` и прав на `crm_internal`. Bootstrap конвергентно задаёт роли без superuser/создания ролей/БД/репликации/BYPASSRLS и с UTC: `crm_owner` — NOLOGIN; `crm_migrations` — LOGIN и единственный член `crm_owner`; `crm_runtime` не имеет членств. Bootstrap снимает прежние прямые database/public-schema grants и лишние memberships всех трёх ролей.

`backend/drizzle/0000_*.sql` и snapshot создаются Drizzle Kit. `0001_security.sql` зарегистрирован как Drizzle custom migration и содержит controlled SQL для default-deny, точных runtime grants и проверки IANA timezone. Раннер читает тот же каталог, нормализует SQL в LF, сверяет checksum, не допускает отсутствующие/переименованные applied migration и сохраняет advisory lock. Маркер `-- inmotion:no-transaction` предназначен для будущих `CREATE INDEX CONCURRENTLY`: перед SQL создаётся состояние `running`; повторный запуск требует ручной сверки и не выполняет слепой replay.

Для Supabase Data API нельзя публиковать `crm` и `crm_internal`. Preview и production используют разные cache-disabled Hyperdrive IDs. Placeholder в `wrangler.jsonc` не является ресурсом: создайте binding через `wrangler hyperdrive create ... --caching-disabled`. Вне default check запускайте `CLOUDFLARE_ACCOUNT_ID=... CLOUDFLARE_API_TOKEN=... SUPABASE_PROJECT_REF=... SUPABASE_ACCESS_TOKEN=... bun run --cwd backend hyperdrive:preflight`. Скрипт читает ID только из `HYPERDRIVE_FRESH` выбранной Wrangler-конфигурации: по умолчанию `wrangler.jsonc`; для отдельного deployment-конфига задаётся `WRANGLER_CONFIG_PATH`, для named environment — `WRANGLER_ENV` (или стандартный `CLOUDFLARE_ENV`). Placeholder и несовпадающие environment отклоняются. Скрипт fail-closed читает Cloudflare REST `.../hyperdrive/configs/{id}`, требует `result.caching.disabled === true` и сверяет origin с `SUPABASE_PROJECT_REF`, затем читает авторитетный Supabase Management API `GET /v1/projects/{ref}/postgrest` и проверяет `db_schema`; секреты и параметры origin не печатаются.

Worker динамически загружает request-scoped adapter; health route не открывает PostgreSQL. Единственная прикладная граница — `withRequestDatabase`, закрывающая pg client через `try/finally`.

`test:db` и `test:db:performance` требуют `TEST_DATABASE_URL`, `TEST_DATABASE_DISPOSABLE_CLUSTER=1` и COMMENT на admin database: `COMMENT ON DATABASE <имя> IS 'inmotion-task002-disposable';`. Это явное подтверждение, что весь кластер disposable: harness временно меняет cluster-global роли и создаёт/удаляет БД, затем удаляет test roles. Маркер базы читается как shared object comment PostgreSQL (`shobj_description`), поэтому harness не допускает ошибочного запуска на непомеченном кластере. Не использовать для shared, preview или production кластеров.

## Целостность, аудит и архивирование

`backend/src/db/integrity.ts` — единственная общая основа для критических составных операций. `executeIdempotentAuditCommand` в одной PostgreSQL-транзакции получает ключ `(scope, operation, key)`, выполняет бизнес-изменение, создаёт аудит и сохраняет terminal HTTP-ответ. SHA-256 стабильного JSON request fingerprint не допускает повторного использования того же ключа для другого payload; конкурентный одинаковый запрос ждёт завершения первой команды и получает сохранённый ответ без второго исполнения. Runtime не имеет прямых прав на `crm.idempotency_keys`: `SECURITY DEFINER` claim-функция создаёт pending key с DB-временем и коротким TTL, а завершение требует 256-bit capability из private table, недоступной runtime SELECT. Capability не является частью response или audit; identity, fingerprint и terminal result после завершения неизменяемы.

Оптимистическая блокировка для пациента выполняется через `SELECT ... FOR UPDATE` и затем `UPDATE ... WHERE id AND version ... RETURNING` в одной транзакции: блокировка делает audit `before` непосредственным состоянием перед `after`, а `WHERE version` остаётся атомарным guard. При несовпадении версии или archive-state `OptimisticLockError` содержит актуальную строку и аудит не создаётся. Новые модули используют этот паттерн вместо отдельного неблокирующего чтения перед `UPDATE`.

`crm.audit_entries` append-only: содержит UTC-момент, nullable `actor_employee_id` до задачи 004, действие, категорию, scope просмотра, сущность, обязательную непустую причину и JSON-снимки before/after. `BEFORE INSERT` trigger игнорирует supplied `occurred_at`/`expires_at` и проставляет их из `clock_timestamp()` и актуальной policy базы. `crm_runtime` может только `SELECT`/`INSERT`; права `UPDATE`/`DELETE` отсутствуют. Избирательное удаление недоступно: защищённая no-argument функция `crm.purge_expired_audit_entries()` удаляет только записи с уже сохранённым `expires_at <= clock_timestamp()`.

Срок хранения задаётся единственной строкой `crm.audit_retention_policies` и меняется только через audited `SECURITY DEFINER`-функцию. Время этого изменения также принадлежит БД, а вызов требует `expectedVersion`: при первом создании это `0`, при устаревшей версии состояние и аудит не меняются, а приложение возвращает актуальную policy. Каждая audit-запись получает собственный сохранённый `expires_at` при вставке; policy может пересчитать его только пока запись не истекла. Поэтому новую policy нельзя применить ретроактивно, чтобы воскресить истёкший аудит. Периодический job может вызвать `purgeExpiredAuditEntries`, но функция не принимает selector и удалит только уже истёкшие записи; прямой runtime `UPDATE` retention policy и `DELETE` по аудиту запрещены.

Архивирование и восстановление не используют table-name SQL: `archiveRecord`/`restoreRecord` работают только с versioned allowlist (`patient`, `medicalCase`, `appointment`, `appointmentSession`, `lead`, `service`, `room`), удерживают row lock до versioned update и создают согласованный audit в той же транзакции. Рабочие выборки должны фильтровать `archived_at IS NULL` — пример `listActivePatients` закреплён интеграционным тестом.
